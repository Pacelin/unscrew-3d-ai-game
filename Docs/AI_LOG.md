# Журнал работы с ИИ

Хронология: что делал человек, что агенты, как проверялось. Отсюда собирается раздел README «Процесс работы с ИИ».

## Инструменты

- **Claude Code (Opus 5.5)** — оркестратор: план, контракты, ревью, мерж.
- **Саб-агенты Claude Code** (`.claude/agents`) — параллельная разработка модулей.
- **UnityMCP** (CoplayDev/unity-mcp) — управление редактором: сцены, префабы, консоль, тесты, скриншоты.
- **dotnet test** — прогон Core-тестов вне Unity за секунды, параллельно по модулям.

## 2026-10-29 — Этап 0–1: план и каркас

**Человек:** создал Unity-проект, поставил URP, импортировал ассеты, подключил UnityMCP, сделал `git init` и `.gitignore`.

**Промпт:**
> Для начала составь план, какие саб-агенты и скиллы нужно создать, как быстрее всего реализовать рабочую игру.

**Агент:** прочитал ТЗ (docx через python/zipfile), README ассетов, проанализировал `Level_XX.json`. Выяснил: id подряд, болтов кратно 3, `sourceLayer` везде 0 — блокировки придётся вычислять самим. Предложил архитектуру «чистое ядро + view» и набор скиллов и агентов.

**Промпт:**
> Пусть с core-dev работают сразу несколько агентов, каждому по механике, которые можно делать параллельно, независимо друг от друга, в связи с этим адаптируй CLAUDE.md и скиллы.

**Решения агента:**
- Контракты (`Scripts/Core/Contracts`) написаны и заморожены **до** запуска параллельных агентов: это единственная точка связи модулей.
- На каждый модуль свой dotnet-проект, который компилирует только `Contracts + модуль + его тесты`, поэтому недописанный код одного агента не ломает сборку другого.
- core-dev работают в git worktree: Unity не видит их промежуточного кода, а редактор свободен для level-designer.

**Проверка:** `test.sh All` — 2/2, Unity EditMode (`Unscrew.Core.Tests`) — 2/2.

**Как оркестратор проверял:**

- До готовности последнего модуля делал **пробное слияние** во временном worktree → `test.sh All` = 150, потом 211. Так заранее проверено, что фейки разных агентов не конфликтуют по именам.
- Настоящее слияние: `git merge --no-ff core/*`. Затем `LevelFactory` (composition root) и интеграционные тесты на **реальных пробейканных уровнях**: бот (`GreedySolver`) проходит все 20 уровней и бесконечный режим, проверены поражение с воскрешением через ExtraSlot и Magnet на настоящей сессии.

**Что агенты сделали не по плану (и правильно):**
- level-designer: алгоритм из скилла (бесконечный луч) дал 494 ложных ребра блокировки. Агент сам заметил это по скриншотам (болт на внутренней стенке чашки «закрыт» противоположной стенкой), заменил луч на короткий коридор и проверку видимости, стало 146 рёбер. Скилл `level-data` обновлён под фактический алгоритм.
- level-designer нашёл, что в проекте не назначен URP-ассет (материалы рендерятся пурпурными) → задача на следующий этап.
- Generation: агент сам поймал собственный баг (бот переиспользовал модель с устаревшей очередью коробок) с помощью стресс-теста на 400 генераций, где самопроверка генератора сравнивается с независимой фейковой сессией.

**Проверка:** `test.sh All` — 279/279 (0.9 с), Unity EditMode `Unscrew.Core.Tests` — 279/279 (4 с).

## 2026-10-29 — Этап 4: играбельный цикл в Unity

**Агент:** unity-integrator (один, ~20 мин, 184 вызова инструментов, в основном UnityMCP).

**Что сделано:** URP для мобильных (до этого не было назначено ни одного pipeline-ассета), сборка `Unscrew.Game`, `LevelCatalog`, `LevelView` (перекраска болтов, коллайдеры, камера по габаритам, вращение), `BoardInput` (луч только по слою Bolt), `TrayView` + `BoardPresenter` (очередь анимаций по `CollectEvent`), падение деталей, `GameFlow`, минимальный HUD, `GameSceneBuilder` (сцена воспроизводимо собирается из меню), `DebugAutoplay`.

**Как проверялось:**
- Бот прошёл **кампанию 1–20 через настоящий view** с анимациями (`DebugAutoplay.RunCampaign`): все Won, число ходов = числу болтов, консоль чистая.
- Поражение проверено на L5 (hard) и L21 (бесконечный режим).
- Агент сам смотрел свои скриншоты и исправлял найденное: болты были мелкими → камера подгоняется по габаритам, а не по описанной сфере; кнопки оверлея съезжали → отцентрованы. MCP-скриншот не захватывает overlay-UI → агент написал свой `DebugCapture`.
- Оркестратор: просмотрел скриншоты `stage4_mid_level`, `stage4_level06_blocked`; проверил `git status`.

**Открытые вопросы на следующие этапы:** не все меши читаемы (`isReadable=false`), поэтому runtime MeshCollider в APK может не создаться (сейчас тап по болтам от этого не зависит); ориентация экрана — AutoRotation; упавшие детали переживают рестарт до 5 с.

**Проверка:** EditMode 279/279, dotnet 279/279, скриншоты `Docs/Screens/stage4_*.png`.

## 2026-10-29 — Этап 4.5: правила корректности уровней и правило поражения

**Промпт (человек, гейм-дизайн):**
> Вводим правила для проверки корректности уровней:
> 1. Шляпки болтов не находятся внутри меша, к которому он прикручен.
> 2. При выкручивании болт не задевает соседние меши (вместо raycast используем SphereCast с радиусом болта, на дистанцию, на которую болт выезжает при выкручивании (длина болта + отступ)).
> Выполни этот прогон на всех уровнях. Поражение при out of space работает некорректно. Поражение должно происходить только в случае, когда не осталось ходов (out of moves)…

**Агенты (параллельно):** core-dev (правило поражения, worktree `core/out-of-moves`, ~9 мин) + level-designer (валидатор и перебейк, Unity, ~14 мин).

**Результаты:**
- Правило 2: граф блокировок строится только по `SphereCastAll` (радиус = радиус шляпки, дистанция = длина × 1.15, старт — над опорной плоскостью шляпки). Геометрию болта агент измерил по мешу `Screw004`. Набор блокеров изменился у 467 из 1611 болтов.
- Правило 1: **161 нарушение** (52 шляпки утоплены целиком: L05 — 25, L18 — 15). Подтверждено скриншотами (`bake2_rule1_*.png`). Сам тест чётности лучей агент проверил на контрольных точках: середина стержня внутри владельца у 258 из 264 болтов, точка далеко снаружи — 0.
- Правило поражения: `Lost` = нет доступного болта, который можно положить в коробку или буфер. Изменения в контракте (доки), `GameSession`, `PuzzleSim`/`GreedyPolicy` и Magnet. Агент нашёл неочевидное следствие: магнит при полном буфере мог «съесть» единственный ход посреди серии → порядок снятия изменён, добавлен тест.
- Агент заметил, что после смены правила даже целенаправленно плохая игра выигрывает L12–13 → отдельная задача на перенастройку сложности.

**Решение оркестратора по правилу 1:** поле `BoltDefinition.headLift` — запечённый сдвиг болта наружу вдоль оси на глубину погружения. Применяется в бейке до свипа и во view при спавне, поэтому граф совпадает с тем, что видит игрок.

**Следующий шаг (параллельно):** level-designer запекает `headLift`; core-dev перенастраивает `DifficultyCurve` по метрике «win rate казуального игрока» (Monte-Carlo на `PuzzleSim`).

**Проверка:** после слияния `test.sh All` 288/288 на перебейканных данных.
