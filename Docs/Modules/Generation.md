# Модуль Generation

`Assets/_Game/Scripts/Core/Generation`, тесты — `Assets/_Game/Tests/Core/Generation`.
Зависит только от `Contracts` (`BoardRules`, `Rng`, `IGameSession`, `ICollector`, `IBoard`, данные уровня).

## Публичный API

| Тип | Назначение |
|---|---|
| `DifficultyCurve : IDifficultyCurve` | `Get(def)` → `DifficultySettings` по `def.number` и размеру уровня. Статика: `EffectiveLevel(n)`, `IsHardLevel(n)`, `Seed(def)`, константы кривой. |
| `LayoutGenerator : ILayoutGenerator` | `Generate(def, settings)` → `LevelLayout`, проходимый по построению. Статистика последнего вызова: `LastAttempts`, `LastMixWindowUsed`, `LastPlannedPeak`, `LastPassedSolverCheck`. Статика `RandomRemovalOrder(def, rng)`. |
| `GreedySolver : ISolver` | `Solve(session)` — бот, читает состояние только через `IGameSession` и ходит только через `Tap`. |
| `GreedyPolicy` | Выбор хода бота: `ChooseMove(sim)`, `Play(sim)`. Одна и та же политика у бота и у самопроверки генератора. |
| `PuzzleSim` | Лёгкая клонируемая модель правил: доступность болтов (через `BoardRules`) + коробки/буфер (правила `ICollector`), без событий. `FromSession(session)` — снимок живой сессии. `HasAvailableMove()` — есть ли ход (правило поражения «ходов нет»). |

## Правило поражения: «ходов нет»

Решение геймдизайнера (заменяет старое «буфер заполнен = поражение»): проигрыш — только когда болты остались,
но **ни один доступный болт** (`BoardRules`) не может уйти ни в открытую коробку своего цвета, ни в свободную лунку.
Полный буфер сам по себе не поражение, пока какой-то доступный болт подходит к открытой коробке.
`PuzzleSim.IsLost`, `GreedyPolicy` (просмотр на шаг) и тестовая `FakeGameSession` следуют этому правилу так же,
как `GameSession`. Циклическая блокировка (болтов нет доступных) — частный случай того же правила.

## Кривая сложности

`e = EffectiveLevel(number)`: 1..20 как есть; 21+ — по кругу 11..20 (бесконечный режим), seed при этом другой.

| Ручка | Туториал (1) | Обычный | Hard (каждый 5-й: 5, 10, 15, 20) |
|---|---|---|---|
| `activeBoxes` | 2 | 3 | 3 |
| `bufferSlots` | 5 | 5 | 4 |
| `mixWindow` | 0 | `1 + (e-2)/4` (1→5) | обычный + 1 |
| `colorCount` | `min(allowedColors, boxes)` | то же | то же |

- Размер уровня: `mixWindow ≤ boxes/3` (маленький уровень не размешать шире трети коробок); `colorCount ≤ boxes`.
- `seed = FNV-1a(number, bolts, parts)` — детерминирован, отличается для повторов в бесконечном режиме.
- Цвета берутся из `allowedColors` уровня (их число уже откалибровано по реальным уровням: 2..10).
- Решение «ближе к Screw Master»: 3 открытые коробки и 5 лунок, hard-уровни отнимают лунку, а не добавляют цветов.

Результат на синтетических уровнях реальных размеров (`RealLevelSizes_DifficultyReport`): `mixWindow` 0,1,1,1,**2**,2,2,2,2,**4**,3,3,3,4,**5**,4,4,5,5,**6**; пик буфера в плане (порядок O) 0 на уровнях 1–4, до 3 на поздних; пик буфера у бота 0 → 3.

## Как генератор гарантирует проходимость

1. **Порядок разборки O.** Случайная топологическая сортировка: на каждом шаге берётся случайный доступный (`BoardRules.IsAccessible`) болт. Если доступных нет, а болты остались — цикл в графе блокировок → `InvalidOperationException`.
2. **Группы.** O режется на группы по `boxCapacity`; группа k = коробка k очереди (`boxQueue[k]`).
3. **Цвета групп.** Количество коробок на цвет сбалансировано (±1), цвет не повторяется среди `activeBoxes-1` предыдущих коробок, если это возможно, так что открытые коробки обычно разноцветные.
4. **Без смешивания (`mixWindow = 0`)** болты, снимаемые в порядке O, идут прямо в открытые коробки своего цвета, и буфер не нужен (тест `MixZero_PlannedOrderNeedsNoBuffer_EvenWithOneHole`: 1 лунка, плановый пик 0; бот может отойти от O и занять единственную лунку — это не поражение, пока есть ход в коробку). Это не берётся на веру: базовая раскраска тоже проигрывается в `PuzzleSim`, и если её пик больше лимита, попытка повторяется с другим O. На тестах такого не случалось.
5. **Смешивание.** Каждая позиция O несёт «жетон» — номер коробки, которой принадлежит болт. Случайные обмены жетонов между позициями, при условии что после обмена каждый жетон k лежит в группе из `[k - mixWindow, k + mixWindow]`. Так болты одной коробки разбросаны по порядку разборки не дальше чем на `mixWindow` групп.
6. **Симуляция после каждого обмена.** `PuzzleSim` проигрывает O с текущей раскраской по правилам коробок и буфера (каскады, очередь, «левая неполная коробка своего цвета»). Обмен откатывается, если игра проиграна или пик буфера больше планового лимита:
   `plannedLimit = bufferSlots - 1 - (isHard ? 0 : 1)` (на обычных уровнях одна лунка всегда остаётся в запасе, на hard можно занять все, кроме последней).
   Так что **существование решения доказано конструктивно**: порядок O — выигрышная последовательность ходов без бустеров с пиком буфера ≤ `plannedLimit < bufferSlots`.
   **После смены правила поражения** буфер в плане никогда не заполняется целиком, значит в каждой позиции O есть ход
   (свободная лунка) — гарантия только усилилась. Запас `plannedLimit` для правил больше не обязателен (по новому правилу
   хватило бы `bufferSlots`), но **оставлен как ручка сложности**: чем меньше плановый пик, тем больше у игрока запас
   на ошибки. Раскладки по тем же seed не изменились (реплей O с пиком ≤ `plannedLimit` ведёт себя одинаково при обоих правилах);
   изменилась только проверка ботом в п. 7: бот теперь может заполнить буфер полностью и продолжить ходом в коробку,
   поэтому некоторые попытки, раньше отбракованные, теперь принимаются раньше.
7. **Проверка ботом.** На готовой раскраске `GreedyPolicy` играет на `PuzzleSim` с нуля. Если бот проиграл, попытка повторяется с новым O, и `mixWindow` уменьшается на 1 каждые 3 попытки; 12-я попытка — `mixWindow = 0`. Если и она не прошла проверку ботом (на тестах такого не было ни разу), возвращается раскладка без смешивания (она проходима по п. 4/6), `LastPassedSolverCheck = false`.

Детерминизм: вся случайность идёт через один `Rng(settings.seed)`, порядок вызовов фиксирован.

## Бот (`GreedySolver` / `GreedyPolicy`)

Каждый ход: `PuzzleSim.FromSession(session)` (читает `Board.IsRemoved`, `GetBoltColor`, `Collector.GetBox/UpcomingColors/GetBufferColor`) → выбор → `session.Tap`.

1. **Болт в открытую коробку**: сначала тот, что дозаполняет коробку (больше `filled`), затем открывающий больше болтов.
2. **Иначе ход в буфер** с просмотром на шаг: кандидат проигрывается на копии, затем все ставшие возможными ходы в коробки. Ключ (меньше — лучше): «ходов нет» после цепочки (`IsLost`; полный буфер с ходом в коробку — не тупик) → занято лунок после цепочки → как скоро цвет появится в очереди → больше снято болтов → больше открыто болтов (освобождение деталей) → id.
3. Нет доступных болтов → стоп, `false`. Цикл ограничен числом болтов + 1.

Генератор и бот используют одну политику, поэтому раскладка, прошедшая самопроверку, проходится ботом, если реальные `Board`/`Collector` следуют тем же правилам, что `PuzzleSim`.

## Что покрыто тестами (64 теста, `test.sh Generation`)

- `DifficultyCurveTests`: туториал, каждый 5-й hard, монотонность обычных уровней, hard как пики, ограничение по размеру, цвета ≤ коробок, seed, бесконечный режим (21→11, 25→15, 30→20, 31→11), ошибки.
- `PuzzleSimTests`: коробка/завершение/активация, каскад из буфера, полный буфер + ход в коробку → не поражение, полный буфер без подходящих доступных болтов → поражение, циклическая блокировка → поражение, блокировка, `Clone/Reset/CopyFrom`, `FromSession`.
- `GreedySolverTests` (на `FakeGameSession` — независимая простая реализация `IBoard`/`ICollector`/`IGameSession` в тестах): тривиальный уровень, приоритет коробок, тесный буфер (нужен цвет из начала очереди и освобождение детали), непроходимый уровень → `false`/`Lost`, циклическая блокировка → `false` без тапов, единственная линия через полностью заполненный буфер (2/2) → победа, переиспользование бота. `FakeGameSession` проверяет «ходов нет» после каждого хода и в конструкторе.
- `LayoutGeneratorTests`: валидация входа, цикл → исключение, порядок O корректен, `mixWindow=0` при 1 лунке (плановый пик 0, бот выигрывает), детерминизм по seed, все цвета используются, цвета ≤ коробок, рост давления на буфер с `mixWindow`, hard-уровень.
- **Синтетические уровни реальных размеров** (`SyntheticLevels.RealSizes`, случайные DAG блокировок: деталь блокируется 0–3 деталями ниже по рангу): 20 уровней × 5 вариантов — валидность, самопроверка, бот на fake-сессии выигрывает, пик < буфера, детерминизм; стресс 20 × 20 вариантов (включая номера бесконечного режима) — самопроверка генератора совпадает с ботом на fake-сессии, fallback не понадобился ни разу.

## Предложения

- **Tests/Core/Shared**: `SyntheticLevels` (генератор DAG-уровней реальных размеров) и `FakeGameSession` лежат в `Tests/Core/Generation/GenerationTestUtil.cs`; их стоит перенести в Shared — пригодятся интеграционным тестам и Boosters.
- **Contracts**: правок не требуется. Возможное улучшение — `ICollector` мог бы отдавать «снимок» для ботов, но через текущий интерфейс всё читается.
- **Integration**: проверить, что реальные `Board`/`Collector`/`GameSession` дают тот же результат, что `PuzzleSim` (например, тот же тест-стресс, но с реальной сессией).
