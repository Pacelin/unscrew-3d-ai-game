# Модуль Generation

`Assets/_Game/Scripts/Core/Generation`, тесты — `Assets/_Game/Tests/Core/Generation`.
Зависит только от `Contracts` (`BoardRules`, `Rng`, `IGameSession`, `ICollector`, `IBoard`, данные уровня).

## Публичный API

| Тип | Назначение |
|---|---|
| `DifficultyCurve : IDifficultyCurve` | `Get(def)` → `DifficultySettings` по `def.number` и размеру уровня. Статика: `EffectiveLevel(n)`, `IsHardLevel(n)`, `Seed(def)`, `TargetCasualWinRate(n)` (целевой win rate казуального игрока), константы кривой. |
| `LayoutGenerator : ILayoutGenerator` | `Generate(def, settings)` → `LevelLayout`, проходимый по построению и подобранный под целевую сложность. Настройки: `TargetDifficulty` (true; false = один кандидат без подбора), `TargetOverride` (NaN = цель из кривой). Статистика последнего вызова: `LastAttempts`, `LastMixWindowUsed`, `LastPressure`, `LastPlannedPeak`, `LastPassedSolverCheck`, `LastCasualEstimate`, `LastTarget`, `LastCandidates`, `LastSearchPressures/Estimates`. Статика `RandomRemovalOrder(def, rng[, diveChance])`, `PressureFromMix`, `WindowOf`, `DiveChance`, `PlannedLimit`. |
| `CasualPolicy` | Модель «казуального игрока» (см. ниже): `Play(sim, rng)`, `WinRate(sim, rng, runs[, out meanPeak])`. Лежит в Core, потому что ею пользуется сам генератор при подборе сложности. |
| `GreedySolver : ISolver` | `Solve(session)` — бот, читает состояние только через `IGameSession` и ходит только через `Tap`. |
| `GreedyPolicy` | Выбор хода бота: `ChooseMove(sim)`, `Play(sim)`. Одна и та же политика у бота и у самопроверки генератора. |
| `PuzzleSim` | Лёгкая клонируемая модель правил: доступность болтов (через `BoardRules`) + коробки/буфер (правила `ICollector`), без событий. `FromSession(session)` — снимок живой сессии. `HasAvailableMove()` — есть ли ход (правило поражения «ходов нет»). |

## Правило поражения: «ходов нет»

Решение геймдизайнера (заменяет старое «буфер заполнен = поражение»): проигрыш — только когда болты остались,
но **ни один доступный болт** (`BoardRules`) не может уйти ни в открытую коробку своего цвета, ни в свободную лунку.
Полный буфер сам по себе не поражение, пока какой-то доступный болт подходит к открытой коробке.
`PuzzleSim.IsLost`, `GreedyPolicy` (просмотр на шаг) и тестовая `FakeGameSession` следуют этому правилу так же,
как `GameSession`. Циклическая блокировка (болтов нет доступных) — частный случай того же правила.

## Кривая сложности

`e = EffectiveLevel(number)`: 1..20 как есть; 21+ — по кругу 11..20 (бесконечный режим), seed при этом другой.

| Ручка | Туториал (1) | Обычный | Hard (каждый 5-й: 5, 10, 15, 20) |
|---|---|---|---|
| `activeBoxes` | 2 | 3 | 3 |
| `bufferSlots` | 5 | 5 | 4 |
| `mixWindow` | 0 | `1 + (e-2)/4` (1→5) | обычный + 1 |
| `colorCount` | `min(allowedColors, boxes)` | то же | то же |

- Размер уровня: `mixWindow ≤ boxes/3` (маленький уровень не размешать шире трети коробок); `colorCount ≤ boxes`.
- `seed = FNV-1a(number, bolts, parts)` — детерминирован, отличается для повторов в бесконечном режиме.
- Цвета берутся из `allowedColors` уровня (их число уже откалибровано по реальным уровням: 2..10).
- Решение «ближе к Screw Master»: 3 открытые коробки и 5 лунок, hard-уровни отнимают лунку, а не добавляют цветов.

`mixWindow` теперь — **стартовое давление** для подбора сложности (см. ниже), а не окончательное значение.

### Метрика сложности и целевая кривая

После перехода на правило «ходов нет» уровни стали мягкими: старая кривая давала 93–100 % побед казуального игрока
почти везде (таблица «до» ниже), а ручки `bufferSlots`/`activeBoxes`/`mixWindow` почти не двигали эту цифру
(сетка на реальных уровнях: 3 коробки, буфер 5→3, mix 1→5 — всего 92 % → 72 %). Причина: на экране одновременно
доступно 15–60 болтов, и среди них почти всегда есть болт цвета открытой коробки.

**Метрика** — win rate «казуального игрока» `CasualPolicy` на `PuzzleSim`: на каждом ходу, если среди доступных болтов
есть подходящие к открытой коробке, с вероятностью **p = 0.65** он берёт случайный из них, иначе — случайный допустимый
болт (в коробку или в свободную лунку). Очередь не читает, буфер не считает. p = 0.65 — «внимательный, но
небрежный» игрок из середины диапазона 0.6–0.7.

**Цель** `DifficultyCurve.TargetCasualWinRate(n)` (по `EffectiveLevel`, так что бесконечный режим повторяет 11–20):

| Уровень | Цель |
|---|---|
| 1 (туториал) | 1.00 |
| 2–4 | 0.95 |
| обычный e ≥ 6 | `0.90 − 0.028·(e − 5)` (0.87 → 0.51 к 19-му) |
| hard (5, 10, 15, 20) | тренд − 0.20 (0.70, 0.56, 0.42, 0.28) |
| после hard (6, 11, 16) | тренд + 0.04 («передышка») |

Решение «ближе к Screw Master»: число коробок (3) и лунок (5, на hard 4) не меняем. В референсе сложность растёт
не от урезания интерфейса, а от того, что нужные цвета закопаны под деталями. Именно это и делают «ныряющий» порядок и
отбор отвлекающих болтов (ниже).

## Как генератор гарантирует проходимость

Генератор работает с **давлением** p (0..14): окно смешивания `WindowOf(p) = (p+1)/2` групп, шанс «нырка»
`DiveChance(p) = 10·(p−1) %` (0..100). `mixWindow = m` из кривой соответствует p = 2m − 1 (окно m, нырок 20·(m−1) %).

1. **Порядок разборки O.** Случайная топологическая сортировка: на каждом шаге берётся случайный доступный (`BoardRules.IsAccessible`) болт; с вероятностью `DiveChance(p)` — случайный из **последних открывшихся** («нырок» вглубь модели). Нырок оставляет рано доступные болты на поздние коробки, поэтому на экране больше болтов, не подходящих ни к одной открытой коробке. Если доступных нет, а болты остались — цикл в графе блокировок → `InvalidOperationException`.
2. **Группы.** O режется на группы по `boxCapacity`; группа k = коробка k очереди (`boxQueue[k]`).
3. **Цвета групп.** Количество коробок на цвет сбалансировано (±1), цвет не повторяется среди `activeBoxes-1` предыдущих коробок, если это возможно, так что открытые коробки обычно разноцветные.
4. **Без смешивания (`mixWindow = 0`)** болты, снимаемые в порядке O, идут прямо в открытые коробки своего цвета, и буфер не нужен (тест `MixZero_PlannedOrderNeedsNoBuffer_EvenWithOneHole`: 1 лунка, плановый пик 0; бот может отойти от O и занять единственную лунку — это не поражение, пока есть ход в коробку). Это не берётся на веру: базовая раскраска тоже проигрывается в `PuzzleSim`, и если её пик больше лимита, попытка повторяется с другим O. На тестах такого не случалось.
5. **Смешивание.** Каждая позиция O несёт «жетон» — номер коробки, которой принадлежит болт. Случайные обмены жетонов между позициями, при условии что после обмена каждый жетон k лежит в группе из `[k - mixWindow, k + mixWindow]`. Так болты одной коробки разбросаны по порядку разборки не дальше чем на `mixWindow` групп.
6. **Симуляция после каждого обмена.** `PuzzleSim` проигрывает O с текущей раскраской по правилам коробок и буфера (каскады, очередь, «левая неполная коробка своего цвета»). Обмен откатывается, если игра проиграна, пик буфера больше планового лимита **или выросла доля «подходящих» болтов**: сумма по шагам O доли доступных болтов, цвет которых есть среди открытых коробок (чем она меньше, тем больше на экране отвлекающих болтов). Доступность вдоль O от цвета не зависит, поэтому список доступных болтов на каждом шаге считается один раз на кандидата (`Frontier`), и проверка обмена стоит один проход по O. Плановый лимит:
   `plannedLimit = bufferSlots - 1 - (isHard ? 0 : 1)` (на обычных уровнях одна лунка всегда остаётся в запасе, на hard можно занять все, кроме последней).
   Так что **существование решения доказано конструктивно**: порядок O — выигрышная последовательность ходов без бустеров с пиком буфера ≤ `plannedLimit < bufferSlots`.
   **После смены правила поражения** буфер в плане никогда не заполняется целиком, значит в каждой позиции O есть ход
   (свободная лунка) — гарантия только усилилась. Запас `plannedLimit` для правил больше не обязателен (по новому правилу
   хватило бы `bufferSlots`), но **оставлен как ручка сложности**: чем меньше плановый пик, тем больше у игрока запас
   на ошибки. Раскладки по тем же seed не изменились (реплей O с пиком ≤ `plannedLimit` ведёт себя одинаково при обоих правилах);
   изменилась только проверка ботом в п. 7: бот теперь может заполнить буфер полностью и продолжить ходом в коробку,
   поэтому некоторые попытки, раньше отбракованные, теперь принимаются раньше.
7. **Проверка ботом.** На готовой раскраске `GreedyPolicy` играет на `PuzzleSim` с нуля. Если бот проиграл, попытка повторяется с новым O, и давление уменьшается на 2 каждые 3 неудачи; 12-я неудача — попытка с p = 0. Если ни один кандидат не прошёл проверку (на тестах такого не было ни разу), возвращается раскладка без смешивания (она проходима по п. 4/6), `LastPassedSolverCheck = false`.
8. **Подбор сложности** (`mixWindow > 0` и `TargetDifficulty`). Для каждого кандидата, прошедшего п. 7, `CasualPolicy` оценивает win rate: 32 прогона, и если оценка в пределах ±0.15 от цели — ещё 64 (итого 96). Стартовое давление `PressureFromMix(mixWindow)`; дальше давление растёт, если кандидат легче цели, и падает, если тяжелее (шаг 2 при ошибке > 0.2, иначе 1). Стоп при ошибке ≤ 0.04 или после 16 кандидатов; возвращается кандидат, ближайший к цели. Разброс сложности между кандидатами с одним давлением большой (на одном уровне p = 5 давал и 18 %, и 94 %), поэтому подбор — это в основном выбор среди случайных кандидатов, а давление смещает их распределение.
   **Гарантия проходимости от подбора не зависит**: любой кандидат прошёл п. 1–7, подбор только выбирает между ними.
   Цель берётся из `DifficultyCurve.TargetCasualWinRate(def.number)`. `LevelFactory.Prepare` выставляет `def.number = displayNumber` на время генерации, так что бесконечный режим получает цель уровней 11–20. Туториал (`mixWindow = 0`) строится одним кандидатом без оценки.
   Стоимость: ~50–350 мс на уровень в Debug на десктопе (зависит от уровня и числа кандидатов).

Детерминизм: построение идёт через `Rng(settings.seed)`, оценка казуальным игроком — через отдельный `Rng(settings.seed ^ const)`; порядок вызовов фиксирован.

## Бот (`GreedySolver` / `GreedyPolicy`)

Каждый ход: `PuzzleSim.FromSession(session)` (читает `Board.IsRemoved`, `GetBoltColor`, `Collector.GetBox/UpcomingColors/GetBufferColor`) → выбор → `session.Tap`.

1. **Болт в открытую коробку**: сначала тот, что дозаполняет коробку (больше `filled`), затем открывающий больше болтов.
2. **Иначе ход в буфер** с просмотром на шаг: кандидат проигрывается на копии, затем все ставшие возможными ходы в коробки. Ключ (меньше — лучше): «ходов нет» после цепочки (`IsLost`; полный буфер с ходом в коробку — не тупик) → занято лунок после цепочки → как скоро цвет появится в очереди → больше снято болтов → больше открыто болтов (освобождение деталей) → id.
3. Нет доступных болтов → стоп, `false`. Цикл ограничен числом болтов + 1.

Генератор и бот используют одну политику, поэтому раскладка, прошедшая самопроверку, проходится ботом, если реальные `Board`/`Collector` следуют тем же правилам, что `PuzzleSim`.

- `PuzzleSimTests`: коробка/завершение/активация, каскад из буфера, полный буфер + ход в коробку → не поражение, полный буфер без подходящих доступных болтов → поражение, циклическая блокировка → поражение, блокировка, `Clone/Reset/CopyFrom`, `FromSession`.
- `GreedySolverTests` (на `FakeGameSession` — независимая простая реализация `IBoard`/`ICollector`/`IGameSession` в тестах): тривиальный уровень, приоритет коробок, тесный буфер, непроходимый уровень → `false`/`Lost`, циклическая блокировка → `false` без тапов, единственная линия через полностью заполненный буфер → победа, переиспользование бота.
- `LayoutGeneratorTests`: валидация входа, цикл → исключение, порядок O корректен, `mixWindow=0` при 1 лунке (плановый пик 0, бот выигрывает), детерминизм по seed, все цвета используются, цвета ≤ коробок, рост давления на буфер с `mixWindow`, hard-уровень. Стресс 20 × 12 вариантов (включая номера бесконечного режима): самопроверка генератора совпадает с ботом на fake-сессии, fallback не понадобился ни разу.
- `DifficultyProbeTests` + хелпер `DifficultyProbe` (`Tests/Core/Generation/DifficultyProbe.cs`: 200 прогонов `CasualPolicy` на уровень, бот, средний пик буфера; `BakedLevels` — загрузчик `Level_XX.json` через System.Text.Json под `CORE_DOTNET_TESTS`, JsonUtility в Unity):

  - среднее по 3 seed на уровнях 4/10/17 в пределах ±15 п.п. от цели;

  - подбор: детерминизм, отключение (`TargetDifficulty = false` → один кандидат, окно = `mixWindow`), `TargetOverride` 0.95 и 0.30 дают разные оценки, обе раскладки проходит бот; «нырок» соблюдает блокировки; значения и форма `TargetCasualWinRate`.

## Предложения

- **Contracts**: добавить в `DifficultySettings` поле `targetWinRate` (float, 0..1). Сейчас генератор сам берёт цель
  из `DifficultyCurve.TargetCasualWinRate(def.number)`. Это обход: оба класса в модуле Generation, а `LevelFactory`
  выставляет `def.number` перед генерацией. С полем кривая передавала бы цель явно, а `mixWindow` остался бы стартовым давлением.
- **Game**: генерация уровня стала дороже (до ~0.35 с в Debug на десктопе на тяжёлых уровнях). Стоит вызывать
  `LevelFactory.Prepare` на экране загрузки или в фоновом потоке (у каждого `LayoutGenerator` свои буферы, общих статиков нет).

- **Tests/Core/Shared**: `SyntheticLevels` (генератор DAG-уровней реальных размеров) и `FakeGameSession` лежат в `Tests/Core/Generation/GenerationTestUtil.cs`; их стоит перенести в Shared — пригодятся интеграционным тестам и Boosters.
- **Contracts**: правок не требуется. Возможное улучшение — `ICollector` мог бы отдавать «снимок» для ботов, но через текущий интерфейс всё читается.
- **Integration**: проверить, что реальные `Board`/`Collector`/`GameSession` дают тот же результат, что `PuzzleSim` (например, тот же тест-стресс, но с реальной сессией).
